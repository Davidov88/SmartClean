# Восстановление после закрытия Codex

Проверено чтением существующей SQLite, без создания Database до первичного аудита:

- 461 389 записей файлов в базе; последний проход перечислил 461 378 файлов и все 5 источников.
- 168 324 частичных отпечатка, 161 332 полных SHA-256.
- 30 195 групп по сохранённым digest и size. В этой цифре возможны hardlinks;
  она не равна числу файлов на удаление или объёму освобождения.
- 0 результатов анализа метаданных: эта отдельная задача не запускалась.
- Последний checkpoint: этап hashing. В момент аудита процессов приложения не было,
  server-error.log был пуст; точный код завершения прежнего процесса не сохранился.

Обнаруженный дефект: прежний запуск worker/window наследовал дерево процессов
управляющей сессии. CREATE_NO_WINDOW только скрывает консоль. Пробный процесс
с CREATE_BREAKAWAY_FROM_JOB всё ещё оказался внутри Windows job, поэтому этот
способ не принят за достаточное исправление.

Теперь запуск выполняет Windows Task Scheduler под текущим пользователем,
интерактивно, без повышения прав, без триггеров, без лимита выполнения и без
остановки при переходе на батарею. У worker проверена цепочка родителей через
процесс Windows вне цепочки Codex. Обе задачи доступны только по запросу.

Создан отдельный согласованный SQLite snapshot через sqlite3.backup:
`.local/recovery/before-recovery-2026-11-02.sqlite3`, 283 992 064 байт.
Исходная база и содержимое файлов не удалялись.

Добавлен resume этапа hashing: без inventory, с проверкой, что предыдущий обход
всех источников завершён. Готовые хэши повторно не читаются из содержимого при
неизменившейся идентичности файла; незавершённый файл/незаписанный пакет вычисляется заново.
Состояние interrupted теперь сохраняет исходный этап, вместо его перезаписи.

Проверки: 16 unit/integration tests, включая продолжение без вызова inventory,
повторное использование готового digest и отказ продолжать неполный обход; JS syntax check.
