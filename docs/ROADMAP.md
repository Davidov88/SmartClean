# SmartClean: план исправлений и развития

Дата: 2026-11-02. Это план, а не перечень уже реализованных функций.
В рамках подготовки этого документа изменены документация и правила публикации;
рабочая база, источники, настройки исключений, процессы и задачи сканирования не менялись.

## 1. Какой результат нужен

Самостоятельное приложение для поиска медиа на всех выбранных дисках, просмотра
точных и похожих копий, управляемого выбора сохраняемых экземпляров и очистки.
Затем — полноценная медиатека с людьми, лицами, событиями, местами, объектами и текстом.
Пользователь должен видеть полезный результат до завершения долгой фоновой работы.

Целевой запуск: собственное окно и устанавливаемое/переносимое приложение, без
Codex, установленного браузера, ручного запуска Python, localhost-вкладки или
неявного создания задач Windows. Самостоятельность не определяется одним языком.
Текущий проект этому требованию соответствует лишь частично: это Python-сервис
с веб-интерфейсом и оболочкой Edge/Chrome; в последнем исправлении добавлены задачи Windows.
Выбор и реализация новой desktop-оболочки — отдельная работа, не выполненная этим планом.

## 2. Что уже пройдено

Последняя прочитанная запись jobs при составлении плана:

| Часть | Состояние |
|---|---|
| Перечисление источников | В предыдущем проходе завершены все 5 источников |
| Перечисленные медиа | 461 378 в проходе; в ранее проверенной базе 461 389 записей |
| Сохранённые полные SHA-256 | 161 332 на момент последнего подробного аудита |
| Группы digest + size | Ранее сохранено 30 195 групп, в том числе возможные hardlinks |
| Последняя задача | `resume`, `phase=hashing`, `state=interrupted` |
| Завершение всего сравнения | Не подтверждено |
| Метаданные/распознавание | Отдельный полный анализ не выполнен |

Это снимок, не непрерывный мониторинг. Для его составления прочитана только запись
последней задачи; хэши и медиа повторно не вычислялись. Разница счётчиков — сохранённый
каталог и конкретный проход; она сама по себе не доказывает пропуск/потерю файлов.
Список всех найденных файлов и список файлов, требующих полного хэша, имеют разные размеры.
Уникальный размер позволяет исключить точный дубль без чтения всего файла.

## 3. Правильная последовательность

1. **Обнаружение / инвентаризация.** Пути, диски/тома, размер, признаки изменения,
   тип по расширению, ошибки доступа. Оригиналы остаются на местах.
2. **Поиск точных дублей.** Одинаковый размер → быстрый отпечаток кандидатов → полный
   SHA-256 подходящих кандидатов. Для маленьких кандидатов — одно полное чтение.
   Совпадения поступают в список по мере подтверждения.
3. **Просмотр и выбор.** Сортировка, фильтры, групповой выбор, правила сохранения,
   оценка логического и реально освобождаемого объёма.
4. **Очистка.** Проверка актуальности файлов и сохраняемой копии, план действий,
   карантин/корзина, журнал и восстановление. При финальном подтверждении точного
   совпадения для операции с оригиналами — побайтовое сравнение при необходимости.
5. **Богатый каталог.** Метаданные, превью, даты, камеры, пропорции, длительность.
6. **Похожие версии и интеллектуальные связи.** Пережатые/изменённые копии, фрагменты,
   люди и лица, места, объекты, OCR, речь и поиск по смыслу.

Шаги 2 и «точные дубликаты» — одна работа: кандидаты постепенно становятся
подтверждёнными совпадениями. Похожие по картинке видео/фото — другой класс результатов.
Приоритет первого выпуска — пригодные к работе шаги 1–4. Метаданные длительности
и разрешения из шага 5 нужны раньше для полезного сравнения видео.

## 4. Очередь работ с критериями готовности

### P0. Вернуть видимый результат и надёжное продолжение

1. Отдельные показатели: всего обнаружено; кандидатов; хэшей уже сохранено;
   проверено в текущем запуске; осталось; групп дублей; ошибки.
2. Исправить скорость resume: ранее найденные 461 тыс. файлов не делить на время
   нового запуска. Для текущего чтения показывать файлы/с и МиБ/с; для кэша — число
   повторно использованных результатов. ETA только при известном объёме текущего этапа.
3. Список уже подтверждённых дублей читается из базы без запуска сравнения. Пагинация,
   фоновые запросы и отмена запроса. Отдельные состояния загрузки/пусто/ошибка/недоступна БД.
   Ошибка запроса не должна выглядеть как отсутствие дублей.
4. Устранить долгие GROUP BY и неоптимальные планы SQL на реальной большой базе.
   Проверять план и время каждого запроса; UI не должен конкурировать с hash worker
   за полное случайное чтение таблицы на USB/HDD.
5. Продолжение после штатного и аварийного завершения: хранить этап, конфигурацию
   источников, алгоритм/версию отпечатка и завершённость отдельных задач. Завершённые
   проверки сохраняются транзакционно; недописанный результат не считается готовым.
   Остановка в середине большого файла может требовать заново прочитать этот файл,
   но не всю коллекцию. Смена правил/алгоритма должна явно инвалидировать нужный кэш.
6. Отчёт CSV/JSON: группа, файл, диск, размер, SHA-256, статус, hardlink, предлагаемый
   сохраняемый экземпляр и причина. Экспорт без удаления оригиналов.
7. Понятное управление процессом: открыть окно, свернуть, приостановить, продолжить,
   остановить сканер, завершить приложение. Не вводить новые фоновые механизмы без
   отдельного решения пользователя. Удаление прежних задач Windows — только отдельным изменением.

**Приёмка:** сохранённые группы видны во время продолжения; принудительное завершение
не обнуляет готовые хэши; счётчики объяснимы; никакого нового полного обхода при resume
завершённой инвентаризации; экспорт совпадает с выборкой базы. Отдельные измерения
первого/повторного открытия на реальной базе около 500 тыс. записей, а не только фикстуры.
Цель отклика страницы — менее 1 с в штатных условиях; холодный старт/ошибки показываются явно.

### P1. Полнота обнаружения и управляемое исключение шума

Разделить **что обнаружено**, **что исключено до чтения** и **что скрыто как шум**.
Полнота всегда относится к выбранным источникам, правилам и доступным файлам.
Недоступные папки, пропущенные форматы и offline-диски отражаются в отчёте.

| Категория | Предлагаемое правило |
|---|---|
| Windows и служебные данные | Профиль системных исключений: проверенные системные корни, корзины, System Volume Information, recovery, системные caches; учитывать старые установки на других томах |
| Установленные приложения/игры | Настраиваемый профиль исключения ресурсов программ; личные скриншоты/записи можно вернуть явным включением |
| Собственные данные SmartClean | База, резервные копии, thumbnails, окружение и кэш всегда отделены от исходной коллекции |
| Производные индексы других каталогов | Локальные исключения путей; не зашивать буквы дисков и личные имена в код |
| Картинки около 1 КиБ | Метка/фильтр «возможный шум», а не доказательство ненужности |
| Маленькие размеры картинки | После чтения метаданных — фильтр по ширине/высоте, например 64×64 и меньше; не удалять автоматически |
| Сохранённые сайты, assets, sprites, thumbnails | Категория источника и отдельный фильтр; явное правило папки, а не вывод только по расширению JPG |
| Короткие ролики/небольшие фото | Не объявлять мусором по одной длительности или размеру; семейные файлы могут быть маленькими |

Для этого ПК пользователь отметил дополнительные исключения:

```text
F:\TheSix
F:\TheSix_Index
F:\TheSix_Index0
```

Первое уже было локальным исключением. Два индекса внесены **в этот план**, а не
в рабочие настройки текущим изменением. Их миниатюры/кропы не должны засорять будущую
выдачу исходной медиатеки. Не читать/менять содержимое этих каталогов ради подготовки плана.

Предложение профилей: «Все медиа» без минимального порога, «Личная медиатека» с
системными/программными исключениями и скрытием мелких assets, «Собственные правила».
Порог, например 4 КиБ, — настраиваемое скрытие/категоризация, не универсальная граница
между фотографией и мусором. В отчёте нужны счётчики и причины каждого исключения.

Поддержка фото/видео/RAW/HEIC/AVIF, потоков и составных форматов задаётся таблицей:
обнаружение по расширению; подтверждение реального формата дешёвой сигнатурой;
декодирование отдельным адаптером; ошибки/неподдерживаемое перечисляются явно.
Поиск файлов без расширения/с неверным расширением — отдельный глубокий режим,
чтобы обычный обход не читал содержимое всех системных файлов. Архивы не распаковывать
неявно. Для Live/Motion Photos и RAW+JPEG хранить связь компонентов.

**Приёмка:** можно объяснить попадание/пропуск любого файла; профиль можно изменить
без потери существующих проверок; шум скрывается обратимо; включённые личные файлы
не пропадают только из-за размера или слова `cache` в родительской папке.

### P2. Практический экран дублей и групповой выбор

- Табличный и визуальный режим. В строке: полный путь, том/диск, размер,
  формат, длительность, разрешение, пропорции, дата съёмки/изменения, статус проверки.
- Сортировки в обе стороны: размер файла; потенциальный выигрыш группы;
  количество копий; длительность; формат/тип; диск; путь; даты; разрешение.
- Фильтры: фото/видео; расширения/фактический формат; диапазон размера/длительности;
  исходный диск и диск сохраняемой копии; только междисковые повторы; папки;
  проверенные/недоступные/изменившиеся файлы; точные/похожие; hidden/noise.
- Несколько диапазонов выбора: файл, группа, видимая страница и вся отфильтрованная
  выдача. Интерфейс явно показывает область, число файлов, объём и сохраняемые копии.
- Предварительный выбор правилом: «выбрать копии на C:, если проверенная сохраняемая
  копия есть на D:». Это не «удалить всё с C:» и не безусловное удаление каждой группы.
- В каждой группе минимум один сохраняемый экземпляр; несколько одинаковых копий
  только на C: требуют отдельного выбора. Offline-файл не считается гарантией сохранности.
- Приоритеты папок/дисков, защищённые источники, исключения внутри группы и ручная коррекция.
- Hardlinks, несколько путей к одному тому, sparse/compressed/reflink и резервные копии
  учитывать отдельно. «Повторный логический объём» не выдавать за точное свободное место.

**Приёмка:** сценарий «оставить D:, выбрать лишние C:» воспроизводим на тестовом
наборе; правило не выбирает последнюю доступную копию; переход между страницами
не теряет и не расширяет выбор; до применения есть экспорт полного плана.

### P3. Контролируемая очистка

Повторная проверка source/keeper непосредственно перед действием; одинаковые полные
digest и актуальные идентичности, при необходимости побайтовая проверка. Блокировать
сменившийся/недоступный keeper, последнюю копию, защищённый путь и перезапись цели.

Корзина Windows и карантин — разные операции. Карантин на том же диске обратим,
но не освобождает место на этом диске; перенос на другой диск требует свободного
места и проверки копии; корзина также не гарантирует немедленное освобождение.
Окончательное удаление — отдельное явно выбранное действие по конкретному плану.

Поштучный журнал с устойчивыми статусами, восстановлением после сбоя и Undo для
обратимых операций. После действия — проверка ожидаемого состояния и фактического
свободного места. При частичной ошибке не терять список выполненных операций.

**Приёмка:** проверены сбой в середине операции, смена keeper после выбора, недостаток
места, конфликт имён, hardlink, частично выполненный план и восстановление карантина.

### P4. Самостоятельная desktop-поставка и производительность

- Зафиксировать решение по оболочке/ядру отдельным ADR: нативный UI или поставляемый
  runtime; никакой зависимости от установленного браузера и Codex. Существующий Python
  — управляющий слой прототипа; это не доказательство оптимального итогового выбора.
- Сравнить стоимость сохранения существующего ядра с переносом узких мест в нативный
  модуль/worker. Сначала профилировать, затем выбирать стек; переписывание само по себе
  не устраняет случайный IO и неудачный SQL. Robocopy рассматривать для проверенного
  переноса, а не как замену поиска произвольно названных одинаковых файлов.
- Явный lifecycle window/worker, один экземпляр, журнал ошибок/выхода, диагностика,
  управляемый фоновый режим и переносимость БД. Полное закрытие Codex и окна —
  обязательные реальные сценарии приёмки, не вывод из наличия CREATE_NO_WINDOW.
- Планировщик по физическим устройствам: лимиты CPU/RAM/IO, последовательное чтение
  HDD, ограниченная параллельность SSD, приоритет крупнейших медиа и пользовательских
  папок перед мелкими assets; измерить полезный результат в единицу времени.
- Версионирование SQLite и миграций, пакетные записи, WAL/checkpoint, резервное
  копирование через SQLite Backup API. Не копировать единственный `.sqlite3` отдельно
  от активного WAL обычным файловым копированием.
- Явные данные/кэш/настройки/логи, кнопки «Открыть папку базы», «Сохранить отчёт»,
  «Резервная копия», «Перенести каталог». Лимит кэша и проверка свободного места.

**Приёмка:** чистый ПК без Python/Chrome/Codex; четырёхчасовой тест; закрытие клиента;
аварийное завершение; перезапуск; обновление приложения с сохранением базы и ручной
разметки. Замеры первого прохода, повторного, resume, холодного/тёплого UI и пики ресурсов.

### P5. Использовать опыт media-cat для полноценного каталога

Проверенные ссылки на исходный проект:

- [README](https://github.com/createsens/media-cat/blob/main/README.md): своя SQLite,
  исходные пути, прокси, транскрипты и разделение оригиналов/генерируемых данных.
- [Модель данных](https://github.com/createsens/media-cat/blob/main/backend/media_cat/models.py):
  Media, MediaFrame, Person, FaceGroup, FaceObservation, Location, Scene, Tag, DetectedObject,
  ChangeHistory, TranscriptRun/Segment, ProxyJob; у FaceGroup есть user_modified.
- [Критерии приёмки](https://github.com/createsens/media-cat/blob/main/docs/acceptance.md):
  сохранение ручных назначений при повторном импорте, поиск FTS5 по людям/сценам/
  тегам/объектам/местам, массовые изменения только выбранного, история/Undo, поведение
  при недоступном источнике. Эти факты описывают media-cat, не реализацию SmartClean.

Последовательность переноса опыта, с проверкой кода, совместимости и лицензий:

1. Дешёвые метаданные и превью: даты, EXIF/GPS, камера, формат, пропорции, длительность,
   FPS, HDR/кодек/звук; ориентация и таймкоды. Версия анализатора и input digest у результата.
2. Отделить содержимое от путей: одна сущность контента на точные копии, несколько
   FileLocation; разметку и анализ не вычислять по каждой физической копии заново.
3. Люди/лица: наблюдение с bbox/кадром/таймкодом; группы; человек; merge/split/ignore;
   ручные назначения сохраняются при новом анализе. Не смешивать «виден» и «говорит».
4. Сцены, события, места, объекты и единый поиск. Координаты GPS отделены от
   предположения модели «пляж»; лица и объекты связаны с интервалами видео.
5. Похожие фото/видео: последовательности кадров/сцен, пережатые версии, фрагменты,
   поворот/кроп/водяные знаки; оценка сходства и объяснение совпадения. Без удаления
   по одному перцептивному отпечатку. У текущего dHash-прототипа явно обозначить лимиты.
6. OCR и транскрипты: отдельные сегменты, спикеры, таймкоды и поиск фраз.
7. Локальный семантический поиск и адаптеры моделей с измерением точности/ресурсов.

Существующую базу/каталог media-cat и F:\TheSix не менять. Интеграция — возможный
экспорт/импорт копии разметки с проверкой, что ручные результаты сохраняются.
Не объединять приложения и не переносить тяжёлые модели до решения базовых задач SmartClean.

## 5. Ближайший полезный выпуск

**Обязательный результат:** открывается сохранённый каталог → видны уже найденные
точные группы → есть сортировки и фильтр C:/D:/другие диски → можно сформировать
план группового выбора → экспортировать его → продолжить только незавершённые проверки.

Следом — операции очистки из P3. Распознавание людей и похожих видео развивает
