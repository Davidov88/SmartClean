# SmartClean: скорость, корректность и стабильность

Дата исследования: 4 ноября 2026. Роль: инженер производительности и надёжности. Это исследование и предложение архитектуры, без запуска сканирования пользовательских дисков и без очистки. Онлайн-источники прочитаны инструментом поиска/чтения страниц, GUI браузера не использовался. Сведения веток main/master могут опережать опубликованный релиз; перед интеграцией требуется фиксация конкретного тега и проверка его возможностей.

## Вывод

Не писать собственный MFT-парсер первым этапом. Сначала сравнить два адаптируемых готовых сканера: **gdu** для обычного обхода и **WinDirStat** для быстрого NTFS/экспорта. Microsoft Sysinternals DU использовать как независимый дополнительный ориентир, а не абсолютную истину. Начать с одного вертикального read-only сценария: обнаружение накопителей → сканирование → раскрытие дерева из сохранённого результата → сохранение и сравнение замеров. Модуль очистки входит в полную v1 после проверки правил, но не в первый прототип.

Это выбор кандидатов для проверки, а не заявление, что один уже победил. Скорость на чужом NVMe ничего не гарантирует для HDD пользователя. Проходной критерий — прежде всего правильные размеры, ссылки и частичные результаты; затем скорость и потребление памяти.

## Готовые проекты

### gdu — первый кандидат обхода

[Репозиторий, MIT](https://github.com/dundee/gdu), [официальная инструкция Windows](https://github.com/dundee/gdu/blob/master/INSTALL.md), [релизы](https://github.com/dundee/gdu/releases).

Go CLI/TUI. Есть Windows binary, Winget/Scoop. README описывает JSON export/import, постоянное хранилище SQLite/Badger, последовательный режим для HDD, отключение удаления/запуска shell/просмотра файлов. При остановке интерактивного сканирования можно оставить полученные результаты. Ошибки чтения отражаются в экспортируемом дереве. README заявляет однократный подсчёт hardlinks. У проекта есть необязательный web-режим — он не нужен и не должен включаться.

Ограничения для решения: поведение Windows junction, cloud placeholders, NTFS allocation и hardlinks нужно проверить отдельно. Общая документация возможностей не заменяет Windows fixture. Экспорт нескольких независимых корней имеет ограничения: безопаснее один том/корень на scanId. Внешнюю схему JSON не считать внутренним контрактом SmartClean; нужен адаптер и тесты импорта. Экспорт в файл сам по себе не гарантирует сохранения при аварийном завершении процесса.

### WinDirStat — первый кандидат быстрого NTFS

[Репозиторий](https://github.com/windirstat/windirstat), [текущий README](https://github.com/windirstat/windirstat/blob/master/README.md), [опубликованный релиз](https://github.com/windirstat/windirstat/releases/latest).

Текущий README заявляет ускоренный elevated NTFS scan, logical/physical sizes и hardlinks, сохранение/загрузку CSV/JSON и команду `/SaveTo`, которая экспортирует и завершает работу. Windows 10 входит в заявленный список тестируемых ОС. Лицензия приложения GPL v3 or later; использование кода и распространение проверять относительно конкретного файла/релиза. Portable-архивы доступны. Утверждение «WinDirStat всегда только медленно обходит папки» по текущему проекту устарело.

Проверить: доступность CLI-функций именно в закреплённом релизе, открытие/неоткрытие окна в export mode, прогресс и отмену, форматы результата, физический учёт hardlinks. Наличие GUI приложения не делает его web-зависимостью, но пользовательское меню должно оставаться консольным.

### dust — простой дополнительный кандидат

[Репозиторий, Apache-2.0](https://github.com/bootandy/dust). Rust CLI с древовидным обзором и ограничением глубины отображения, Windows install указан проектом. Подходит как эталон простоты вывода и дополнительный кандидат быстрого обхода. Не выбран первым: для SmartClean важнее полный повторно используемый snapshot и сигнализация неполноты, чем красивый одноразовый вывод. Формат машинного экспорта и семантику размеров конкретного Windows release ещё нужно проверить.

### dua-cli — сильный TUI-референс

[Репозиторий, MIT](https://github.com/Byron/dua-cli). Rust, параллельный обход, interactive drill-down, Windows binaries. README отмечает необходимость nightly при самостоятельной Windows сборке; это не означает, что пользователю нужен Rust для готового binary. В текущей документации есть предупреждение об экспериментальности API библиотеки dua. Поэтому предпочесть внешний процесс/закреплённый CLI библиотечному встраиванию, пока стабильность API не подтверждена. Не назначать победителем по заявлениям о скорости на SSD.

### disktree — MFT-референс, не готовое ядро

[Репозиторий, MIT OR Apache-2.0](https://github.com/dmoore-dwmmholdings/disktree). Windows-first Rust TUI с MFT и обычным обходом. Полезен как открытый пример двух сканеров. Но проект молодой: при просмотре 18 commits и один star, что само по себе не дефект, но недостаточно свидетельств эксплуатации. README явно оговаривает apparent-only sizes, отсутствие ADS, разный учёт hardlinks в MFT и walk. Ссылки не раскрывает. Эти ограничения мешают использовать его без изменений для объяснения физического заполнения диска. Авторские бенчмарки полезны лишь как гипотеза для собственных измерений.

### Sysinternals DU — независимая контрольная точка

[Документация Microsoft](https://learn.microsoft.com/en-us/sysinternals/downloads/du). Есть CSV с DirectorySize и DirectorySizeOnDisk. `-l` задаёт глубину информации; `-n` отключает рекурсию. `-u` включает подсчёт каждого экземпляра hardlink. Распространяется по условиям Sysinternals, не считать open-source библиотекой и не включать binary в пакет без проверки условий. Полезен для сверки, но отсутствие документированного стабильного incremental/progress API ограничивает роль основного движка.

### WizTree — контроль скорости, не обязательная зависимость

[Официальный сайт](https://diskanalyzer.com/), [официальное лицензирование](https://diskanalyzer.com/licensing). Проприетарный проект; бесплатность личного использования не равна разрешению коммерческого использования и перераспространения. Можно включить в добровольное сравнение производительности отдельно от open-source основы. Не привязывать универсальность SmartClean к этому продукту.

## Что действительно означает «быстро»

Первый этап: инвентаризация томов без рекурсивного сканирования. Нужна связь PhysicalDisk/Disk → Partition → Volume, а не предположение «буква = физический диск». [Get-PhysicalDisk](https://learn.microsoft.com/en-us/powershell/module/storage/get-physicaldisk) работает через доступные Storage Management Providers; [Get-Volume](https://learn.microsoft.com/en-us/powershell/module/storage/get-volume) имеет ограничения для dynamic volumes. Unknown/virtual/RAID должны быть допустимыми результатами. Нет MediaType — не угадывать SSD по названию. C: и D: могут быть разделами одного устройства, следовательно одновременно нагружать их двумя полными сканами неразумно.

Для обычного обхода: поточная обработка, ограниченная очередь, ограниченный параллелизм и один учёт каждого физического корня. На HDD — последовательный или очень малый параллелизм; на SSD — измеряемый ограниченный параллелизм. Не строить миллионы PowerShell объектов в pipeline, не применять повторный Get-ChildItem -Recurse для каждого родителя и потомка. PowerShell годится для меню/discovery/оркестрации, горячий обход лучше выполнять готовым нативным процессом или скомпилированным модулем.

NTFS MFT обычно позволяет получать карту без открытия каждой папки, но не универсален для FAT/exFAT/ReFS/SMB. [FSCTL_ENUM_USN_DATA](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_enum_usn_data) перечисляет NTFS записи; [USN_RECORD_V2](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-usn_record_v2) содержит имена, идентификаторы, атрибуты и причины изменений, но **не размер файла**. Обещать полную карту размеров одним USN-enum вызовом неправильно: нужны дополнительные metadata APIs или корректный raw MFT parser. Собственный raw parser значительно повышает объём проверки NTFS-особенностей.

## Корректность важнее красивой суммы

Контракт хранит отдельно logicalBytes, allocatedBytes (nullable), uniqueAllocatedBytes (nullable), allocationMethod и allocationConfidence. Нельзя молча подписать logical length как «занято на диске». [GetCompressedFileSizeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getcompressedfilesizew) учитывает compressed/sparse storage, но имеет отдельные правила для обычных файлов и следует за symbolic link. Поэтому один этот вызов не заменяет всю политику allocation/links. Маленькие resident files, sparse/compact/cloud placeholders и hardlinks проверять fixture.

Reparse point нужно записать как ссылку с target и типом, не переходить автоматически. Перенесённая папка на D: не должна увеличивать физическую сумму C:. Mount point другого тома — отдельная сущность. Путь, имя и физическая сущность файла — разные вещи: для hardlinks нужна идентичность volume+fileId. Если движок не даёт надёжной дедупликации, результат помечать как apparent/incomplete; не скрывать это.

[Документация .NET EnumerationOptions](https://learn.microsoft.com/en-us/dotnet/api/system.io.enumerationoptions) позволяет управлять пропуском атрибутов и inaccessible entries, но простое IgnoreInaccessible не сохраняет полноценный журнал причин. SmartClean должен явно учитывать denied, disappeared, offline, unsupported и ошибки перечисления, а не записывать ноль как точный размер. Системные метаданные, VSS и неохваченные защищённые зоны способны объяснять разницу между used volume bytes и суммой видимых файлов; неизвестную разницу показывать отдельно.

## Snapshot и сравнение

Отображение трёх уровней не ограничивает глубину полного подсчёта. После одного прохода агрегаты всех родителей строятся снизу вверх; drill-down читает snapshot. При остановке сохраняется partial snapshot с областями покрытия, а не «полный отчёт» с незаметными пропусками. Досканирование — отдельная операция с новым временем наблюдения. У живой системы замер имеет startedAt/finishedAt, он не атомарный.

Snapshot: schemaVersion, scanId, hostId, volumeId, volumeSerial, mountPaths, engineVersion, settingsHash, timestamps, status, coverage, errors, nodes, rootTotals. Node: id, parentId, path, kind, fileId, links, sizes, counts, attributes, observedAt. Идентификация тома не только буквой; путь не единственный идентификатор файла. Сравнение запрещено молча продолжать при несовместимой семантике allocation/exclusions/coverage.

Еженедельный полный snapshot надёжнее раннего внедрения USN-инкрементов. Позже USN может ускорить изменение индекса, но [USN_JOURNAL_DATA_V0](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-usn_journal_data_v0) требует проверки JournalID и границ доступных USN. При потере непрерывности нужен baseline rescan. Не создавать/менять/удалять journal ради диагностики. Из роста папки нельзя доказать процесс-виновник; точная атрибуция процессов — отдельный режим наблюдения в будущем.

## Стабильность и переносимость

PS5.1 bootstrap не должен зависеть от установки PS7. [Microsoft различает Windows PowerShell/.NET Framework и современный PowerShell/.NET](https://learn.microsoft.com/en-us/powershell/scripting/what-is-windows-powershell). Минимальная ОС и архитектуры фиксируются явно. «Запускается на обычной Windows10» и «официально поддерживается текущим runtime» — разные утверждения; не назначать современный .NET/PS7 обязательным без проверки матрицы. Нативный scanner process упрощает независимость от runtime меню.

Потоковые события: Progress, ItemBatch, Warning, Completed, Cancelled, Failed. Ограниченный буфер, сообщения максимум несколько раз в секунду, отсутствие псевдоточного процента при неизвестном числе файлов. Отмена должна остановить выдачу новых задач; UI остаётся отзывчивым. Crash-safe запись во временный файл с атомарным завершением, версия схемы, проверка свободного места перед записью, retention истории. Предусмотреть read-only запуск без admin и отдельный осознанный elevated scan; права не менять и ownership не перехватывать.

Операции очистки живут в отдельном модуле. Scan provider не должен иметь разрешения Delete. Позднее executor повторно проверяет root/identity/reparse перед действием, чтобы устаревший путь не удалил новые данные. Размер кандидатов не равен реально освобождённым байтам: hardlinks, открытые handles, корзина и параллельная работа программ меняют результат.

## Первый проверяемый этап и бенчмарк

1. Закрепить releases и checksums двух кандидатов, проверить license notices. Не устанавливать их автоматически в рамках текущего брифа.
2. Создать отдельную искусственную тестовую папку с известным содержимым: много мелких файлов, глубокая вложенность, кириллица/длинные имена, sparse/compressed, hardlink, junction наружу и цикл, недоступная папка, удаляемый во время обхода файл. Cloud placeholder — дополнительная отдельная проверка без принудительной загрузки.
3. Сравнить gdu, WinDirStat и DU на одинаковой области и одинаковой семантике; отдельно отметить unresolved metadata и protected areas. Не принимать совпадение двух неправильных logical totals за доказательство физической точности.
4. После разрешённого перехода к реализации измерить wall time, time to first useful output, peak RAM, CPU, output size, cancel latency, cold/first vs warm cache. Не выдавать warm-cache цифры за первый запуск; не сбрасывать системный cache принудительно. Затем проверить реальные NTFS SSD/HDD и exFAT/removable fallback без удаления данных.
5. Первый готовый сценарий: portable launch → inventory → выбор тома → прогресс → top tree depth3 → cached drill-down → snapshot → сравнение двух замеров. Нет веб-компонентов и нет очистки в прототипе.

Предлагаемые цели для приёмки прототипа, пока не обещания: первое состояние discovery до нескольких секунд на обычной исправной конфигурации; обновление прогресса не реже секунды; UI отмены реагирует немедленно, остановка сканера измеряется; drill-down из готового индекса без повторного обхода, целевой отклик <300мс; нет следования junction; fixture суммы совпадают с ожидаемой семантикой. Итоговый engine выбирается по проверке, а не по числу stars.

## Peer review: предварительный консенсус со вторым агентом

Агент удобства и развития подтвердил `/SaveTo`, ускоренный NTFS, Windows10 и GPLv3+ в [README именно release/v2.9.3](https://github.com/windirstat/windirstat/blob/release/v2.9.3/README.md), опубликованного 11 октября 2026. Значит эта часть shortlist не зависит только от main. Практический gate остаётся: запуск экспорта не открывает неожиданное окно/диалог, в том числе при ошибке; exit status, partial behaviour и нормализованный scope/time корректны.

Оба агента согласовали первые кандидаты gdu + WinDirStat, вертикальный read-only срез и отложенный выбор победителя после измерений. Остановка с сохранением обнаруженного не означает возможность возобновить с того же места после перезапуска. Для скорости HDD/SSD важен физический диск, а не только буква тома.

Отчёт второго агента прочитан: [usability-evolution.md](usability-evolution.md). Разногласий по старту нет. Взаимная критика добавила два важных условия: собственное хранилище SmartClean отмечать отдельной категорией self-usage и исключать из пользовательского growth с явным отображением исключения; обновление ветки не изменяет исходный immutable snapshot, а создаёт новое наблюдение/снимок с отдельными временем и coverage. Complete означает завершение заданной области, а не атомарный образ живой файловой системы. Формат и размер хранилища, а также выбор движка остаются решениями после измерений. При перераспространении GPL binary условия лицензии сохраняются и для отдельного процесса.
