# SmartClean: удобство и развитие

Дата исследования: 4 ноября 2026. Роль: агент удобства и развития. Это исследование и проектный бриф, не реализация. Пользовательские диски не сканировались, очистка не выполнялась, браузер не открывался. Источники получены через поиск, чтение страниц и GitHub REST/raw.

## Вывод

Начать с собственной небольшой русской терминальной оболочки и сменных адаптеров существующих сканеров. Первые два кандидата для проверки — **gdu** и **WinDirStat 2.9.3 в режиме экспорта**. Выбирать основной движок после проверки на Windows 10; не писать собственный MFT-парсер на первом этапе. Готовые программы решают важную часть подсчёта, но ещё не дают весь требуемый сценарий: обнаружение оборудования, сопоставимые недельные замеры, понятное объяснение кандидатов и управляемые разрешения на очистку.

Минимальный первый результат: обнаружить накопители → выбрать том → один раз собрать карту → показать три уровня → раскрывать ветки из сохранённой карты → сохранить снимок → сравнить с новым снимком. До прохождения этого сценария удаление не подключать.

## Проверенные аналоги

### gdu — кандидат №1 на универсальный обход и готовый терминальный просмотр

MIT. Имеет терминальную навигацию, JSON export/import, сохранение в БД и последовательный режим для HDD. Есть опции запрета удаления, запуска оболочки и просмотра содержимого. Документация описывает сохранение найденного при остановке и признак read_error в экспорте. Эти возможности хорошо совпадают со сценарием SmartClean, но ещё требуют проверки именно Windows-сборки и её версии. Наличие web-режима не требует его использования: SmartClean его не включает. В опубликованных сравнительных тестах проекта использовалась другая ОС/среда; переносить цифры на этот ПК нельзя. [README](https://github.com/dundee/gdu), [исходный README](https://raw.githubusercontent.com/dundee/gdu/master/README.md).

Проектное решение: собственная модель снимка поверх JSON движка. Не считать его внутреннюю SQLite-схему стабильным контрактом SmartClean. Экспорт нескольких корней может иметь ограничения; надёжнее отдельное задание на том и общий манифест.

### WinDirStat — кандидат №2 на ускоренный NTFS

GitHub API показал последний релиз **release/v2.9.3**, опубликованный 11 октября 2026. Проверен README именно этого тега: ускоренный локальный NTFS при повышенных правах, логический/физический размер, CSV/JSON и `/SaveTo`, который сохраняет отчёт и завершает работу. Windows 10 указан среди поддерживаемых ОС. Лицензия приложения GPLv3 или новее. Значит CLI-возможности не являются лишь обещанием ветки разработки. Требуются практические проверки отсутствия окон, диалогов, обработка ошибок и формата данных. [Релиз](https://github.com/windirstat/windirstat/releases/tag/release/v2.9.3), [README релиза](https://github.com/windirstat/windirstat/blob/release/v2.9.3/README.md).

Проектное решение: использовать отдельным исполняемым адаптером с закреплённой версией и лицензией в поставке. Копирование кода в собственное ядро не планировать без отдельного решения о лицензировании.

### Остальные

- **dust**, Apache-2.0: простой обзор крупных веток, глубина вывода, JSON. Хороший резервный CLI и пример лаконичного вывода. Не даёт готовой всей системы наблюдения и согласований. [Репозиторий](https://github.com/bootandy/dust).
- **dua**, MIT: Windows-бинарники, интерактивная навигация и исследование дерева. Документация отмечает ограничения отображения и изменения API библиотеки; CLI предпочтительнее прямого связывания с экспериментальным API. Полезен как UX-референс и резерв. [Репозиторий](https://github.com/Byron/dua-cli).
- **Sysinternals DU**: официальный небольшой CLI Microsoft, CSV, настраиваемая глубина вывода, размер и размер на диске, политика учёта hardlink. Подходит как независимая проверка на тестовых данных; не заменяет своё меню и историю. [Документация](https://learn.microsoft.com/en-us/sysinternals/downloads/du).
- **WizTree**: CLI-экспорт документирован, однако бесплатность ограничена личным использованием, для коммерческой среды другие условия, для включения в собственный пакет требуется distribution license subscription. Не делать обязательным компонентом универсального бесплатного комплекта. Неофициальные домены из поисковой выдачи не использовать. [Руководство](https://diskanalyzer.com/guide), [EULA](https://diskanalyzer.com/eula).
- **Everything ES**: удобен при уже имеющемся индексе, но требует установленного и запущенного Everything. Это дополнительный адаптер, а не универсальное условие первого запуска. [CLI requirements](https://www.voidtools.com/support/everything/command_line_interface/).
- **TreeSize**: полезный функциональный ориентир; функции и лицензии зависят от редакции. Free на текущей странице ограничен личной некоммерческой средой, сравнение по времени и дубли представлены в платной редакции. Не считать бесплатный выпуск открытым движком для встраивания. [Редакции](https://www.jam-software.com/treesize/editions.shtml).

## Интерфейс

При запуске не начинать полный скан автоматически. Первый экран показывает доступные накопители/тома, свободное место, дату последнего снимка, место хранения результатов и доступные режимы. Выбор результатов по умолчанию не должен молча засорять системный диск: проверить доступное место и предложить подходящее расположение. Не выбирать E: по имени на других ПК.

Меню:

1. Обзор дисков и крупнейших веток.
2. Углубиться в выбранную ветку последнего снимка.
3. Изменения с прошлого замера.
4. Кандидаты на очистку и согласованные правила.
5. Дубли — следующий этап.
6. Организация и перенос — следующий этап.
7. История, настройки, экспорт.

Экран дерева: текущий путь и хлебные крошки; сортировка по занимаемому месту; размер, доля, количество файлов; Enter — раскрыть; Back — выше; обновление выбранной ветки отдельным явным действием. Длинный путь можно раскрыть/скопировать. Размер на диске и логический размер имеют отдельные подписи. Три уровня — начальное представление, а не предел учёта файлов.

Во время работы: этап, прошедшее время, счётчик обработанного, ошибки и кнопка остановки. Не показывать выдуманные проценты/ETA при неизвестном общем количестве. Найденное отображать постепенно, но помечать предварительным. UI должен оставаться отзывчивым.

Каждый снимок явно показывает:

- complete / partial / cancelled / failed и причины;
- время начала и окончания, возраст данных;
- какие тома/корни включены и исключены;
- метод/версию сканирования и уровень прав;
- недоступные ветки и неизвестные размеры;
- логический или выделенный объём, политику ссылок;
- учтённые файлы отдельно от общего занятого места тома.

Разницу между общим занятым местом и суммой файлов не называть мусором: системные метаданные, недоступные данные и другие причины требуют объяснения. Сохранение частичных результатов не равно возможности продолжить скан с места остановки. Последнюю функцию обещать только после проверки адаптера.

## Терминальная технология

Начать с простого числового меню и совместимого текстового представления; стрелки, цвет и Unicode — удобные дополнения, не условие запуска. Русские пути и сообщения обязательно проверить в Windows PowerShell, cmd/ConHost и Windows Terminal. Для автоматизации те же операции доступны без интерактивного меню и возвращают машиночитаемые результаты/коды завершения.

Windows PowerShell 5.1 и PowerShell 7 имеют разные .NET-основы и несовпадающие возможности; нельзя молча использовать PS7-синтаксис в скрипте для штатного Windows PowerShell. Рекомендация: тонкий совместимый launcher/меню и исполняемый сканер отдельно; либо самостоятельный .NET CLI, если измерения покажут преимущество. Runtime и минимальная сборка Windows фиксируются после проверки. [Microsoft: различия](https://learn.microsoft.com/en-us/powershell/scripting/whats-new/differences-from-windows-powershell).

Для будущего расширенного терминального экрана доступны MIT-проекты [Spectre.Console](https://github.com/spectreconsole/spectre.console) и [Terminal.Gui](https://github.com/tui-cs/Terminal.Gui). Первый удобен для меню/прогресса, второй для полноценного дерева и панелей. Их нельзя смешивать с обязательным PowerShell 5.1 без проверки совместимости. Self-contained .NET снимает требование установки runtime, но увеличивает пакет; single-file тоже имеет ограничения публикации. [Microsoft: deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview).

## Контракты и границы модулей

Это предлагаемый собственный дизайн, не свойства сторонних проектов.

- InventoryProvider: оборудование → разделы → тома, стабильные идентификаторы, точки монтирования и признаки неизвестных данных. Буква диска — подпись/маршрут, не личность накопителя. Для сложных конфигураций данные могут быть неполными: Microsoft отмечает ограничения Get-Disk для dynamic disks. [Get-Disk](https://learn.microsoft.com/en-us/powershell/module/storage/get-disk).
- ScannerAdapter: capabilities, validate request, scan, progress, cancel, итог со статусом и ошибками. Capability flags должны различать полные файловые записи, folder-only, allocated size, ссылки, IDs, partial export и resume.
- SnapshotStore: immutable снимки, versioned manifest, query children/top, атомарное завершение, контроль места и retention. Большие деревья не держать исключительно PowerShell-объектами.
- DiffService: сравнивает лишь сопоставимые scope/metric/policies; при различии отмечает ограничение, а не выдаёт ложный прирост. Отсутствующий том — «не наблюдался», а не «всё удалено». Rename по возможности определяет по identity, иначе честно показывает неоднозначность.
- CleanupRule: стабильный id и версия, обнаружение владельца/категории, обоснование, риски, условия закрытия программы, способ очистки, исключения. Не произвольные удаляющие команды в JSON.
- Planner: снимок → конкретные кандидаты с путями/объёмом/условиями → план без изменений.
- Executor: перед действием заново проверяет путь, тип, ссылки, условия и разрешение именно на эту версию правила; пишет структурированный итог каждого объекта.
- History: события диагностики и действий отдельно от пользовательских представлений. Одинаковые данные обслуживают меню, CLI, будущий UI.

Минимальный manifest: schemaVersion, appVersion, hostId (локальный, без передачи), snapshotId, timestamps UTC + отображение в local timezone, volume identity/mountpoint, engine/version, scope/exclusions, sizeMetric, linkPolicy, completeness, error counts, capabilities. Схема строк содержит nodeId/parentId, имя/путь, тип, logicalBytes, allocatedBytes nullable, completeness, link target/identity nullable. Ноль и неизвестное значение различаются.

Не строить framework произвольных плагинов в v0. Достаточно небольшого набора типизированных внутренних модулей и адаптеров. Контракты позволяют расширение без загрузки непроверенного исполняемого кода.

## Очистка и еженедельный контроль

Карточка кандидата: «что это → какая программа → почему считается кэшем → последствия → оценка освобождения → разрешён ли этот rule». Пользователь согласует конкретные правила и границы, а не целые AppData или все старые файлы. Обновление правила с расширением области не наследует старое согласие автоматически. Download, история чатов, профили, virtualenv/node_modules, базы и результаты задач по умолчанию не становятся безопасным мусором.

Снимок хранится отдельно от новых файлов после него. Перед удалением план актуализируется, устаревший список не исполняется вслепую. Корзина на том же диске не гарантирует освобождения; перенос на том же диске также не освобождает его. Для невосстановимой очистки кэша это честно указать. Итог различает удалённые байты по объектам и изменение свободного места, поскольку другие программы продолжают писать.

Недельные снимки запускаются вручную или позднее через отдельную настройку планировщика, без постоянного фонового процесса на первом этапе. Сравнение размера не доказывает виновную программу. Для причинности нужен отдельный диагностический режим, а не придуманный процесс-владелец по названию каталога. Собственный каталог снимков исключается из анализа роста с видимым указанием исключения, чтобы аудит не создавал ложный всплеск. Обновление отдельной ветки создаёт новую версию с собственным временем наблюдения; исходный снимок не мутирует, а разная свежесть веток видна.

## Gate выбора движка и первый этап

1. Закрепить release binaries/checksums/licenses. Проверить Win10/11, user/admin, UTF-8/кириллицу/длинные имена, без установки PS7 и без браузера.
2. На контролируемом наборе проверить junction на другой том и цикл, hardlink, sparse/compressed, пустые/недоступные ветки, изменение файлов во время скана. Ошибки не должны превращаться в 0 байт.
3. Для gdu и WinDirStat проверить нормализацию результатов, экспорт/импорт, отмену, чистый CLI без диалогов и безопасность переданных путей.
4. Измерить time-to-first-result, полное время, пиковую RAM, размер snapshot, скорость cached drilldown и нагрузку SSD/HDD. Числа из чужих Linux-бенчмарков не принимаются за результат Windows.
5. Подтвердить вертикальный срез inventory → read-only scan одного тома → depth3 → cached drilldown → save/load → второй scan → diff. Только затем выбрать default engine.
6. После успешного среза добавить малый набор правил очистки и executor. Только после их проверки — полная v1. Дубли/переносы остаются v2.

Критерии удобства: другой ПК и другие буквы дисков не требуют редактирования кода; отмена и возврат понятны; сохранённое дерево раскрывается без повторного обхода; partial видно на всех зависимых экранах; сравнение объясняет несовместимость; выбранный путь и последствия удаления видны до действия. Для скорости нужны измеренные бюджеты после PoC, а не обещание «идеально на всех ПК».

## Peer review

С агентом скорости согласованы кандидаты gdu + WinDirStat, read-only вертикальный срез, различение logical/allocated и отсутствие обещания resume без проверки. Агенту переданы результаты проверки релизного тега WinDirStat. Основное дополнение со стороны UX: качество и происхождение данных должны быть частью контракта и постоянно видны, иначе быстрый, но неполный результат создаёт ложную уверенность.

После чтения отчёта коллеги приняты уточнения:

- complete означает завершение выбранного scope с обозначенной полнотой, не атомарный снимок живой файловой системы: хранится интервал startedAt/finishedAt.
- БД и импорт gdu не доказывают ограниченное потребление RAM или восстановление после crash; это измеряемые свойства конкретного адаптера. Собственный формат манифеста нужен сразу, а отдельный тяжёлый индекс/БД только если его необходимость подтверждена.
- Отдельный exe и notices не заменяют соблюдение GPL при распространении WinDirStat; условия исходников и поставки фиксируются для выбранного релиза.
- Каталог результатов настраивается один раз с возможностью смены; retention и контроль места обязательны.

Неразрешённый экспериментальный вопрос: какой движок реально проходит Windows allocation/reparse/cancellation gate и даёт приемлемые время/RAM/размер снимка. Обещания «идеально» до проверки не даются.
